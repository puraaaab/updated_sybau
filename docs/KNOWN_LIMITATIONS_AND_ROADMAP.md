# SYBAU VMS — Known Limitations, Architectural Boundaries & Engineering Roadmap

## Executive Summary

This document provides a transparent, rigorous technical disclosure of the architectural design decisions, hardware boundaries, AI model fallbacks, and security scope assumptions implemented in **SYBAU VMS v1.0**.

Rather than masking system trade-offs as flaws, this report outlines the explicit engineering rationale behind each decision and details the strategic upgrade roadmap for enterprise deployment.

---

## 1. GPU Concurrency & Pipeline Serialization (`gpu_lock`)

### Current Implementation & Micro-Batching Mitigation
* **Architecture:** In single-node environments (e.g., single workstation with an NVIDIA RTX GPU), concurrent CUDA calls across multiple worker threads can trigger driver context switching overhead and CUDA race conditions.
* **Mitigation:** The system uses a centralized `InferenceScheduler` combined with a thread-safe `gpu_lock` inside `model_manager.py`. Multi-camera frames arriving within a 20ms window are dynamically micro-batched into single GPU forward passes.
* **Production Scaling Roadmap:** For multi-node enterprise deployments (50+ cameras), the serialized `gpu_lock` model will be replaced by **NVIDIA DeepStream SDK** and **Triton Inference Server** (gRPC / shared memory queues), allowing zero-copy TensorRT execution across dedicated GPU clusters.

## 2. Vehicle Color & Attribute Recognition (`color_method`)

### Primary vs. Fallback Classification Architecture
* **Primary Method (`color_method: "clip"`):** Uses a pre-loaded OpenCLIP zero-shot vision-language model (`clip-ViT-L-14`). Cropped vehicle images are embedded and compared against text prompt embeddings (`"a photo of a {color} vehicle"`). This provides high accuracy under variable sodium-vapor lighting and outdoor CCTV glare.
* **Heuristic Fallback (`color_method: "hsv_fallback"`):** When CLIP inference is disabled (e.g. low-resource edge deployment mode) or fails, the system invokes `detect_vehicle_color_fallback()`, which computes OpenCV HSV median color thresholds.
* **Transparency Guarantee:** Every database record (`Vehicle.vehicle_color`) and API response includes the `color_method` attribute, ensuring law enforcement operators and forensic auditors can distinguish deep neural inference from heuristic fallbacks.

## 3. Speed Metrics & Physical Calibration (Pixels/Sec)

### Metric Scope & Homography Boundaries
* **Current Metric:** Object speed is calculated in relative normalized pixel displacement per second (`px/s`).
* **Engineering Boundary:** Converting pixel speed to real-world velocity (e.g., $km/h$) requires **3D-to-2D camera homography calibration** (defining real-world ground-plane distances per camera angle) and lens distortion correction.
* **Roadmap:** Future releases will introduce an interactive camera calibration UI allowing operators to draw 4-point reference quads with measured real-world lengths (e.g. 5-meter lane marking references), computing homography matrix $H$ to transform pixel deltas into calibrated velocity.

## 4. Forensic Evidence Cryptographic Hash Model

### Dual Hash Architecture (Clip vs. Source Segment)
Every forensic ZIP export generated by `event_export.py` contains two distinct cryptographic signatures in `metadata.json` and `chain_of_custody.txt`:

1. **`exported_clip_sha256`:** The SHA-256 hash of `evidence_clip.mp4` (the keyframe-aligned video clip extracted for the alert window).
2. **`source_segments_sha256`:** A mapping of SHA-256 hashes for the raw, un-edited continuous recording segment file(s) stored on disk from which the clip was extracted.

### Legal Chain of Custody Rationale
Slicing a sub-clip from a 15-minute continuous recording file changes the byte length and container offset, producing a different file hash than the source segment. Storing **both hashes** in the evidence manifest allows defense attorneys and court experts to independently verify:
- The byte-level integrity of the exported evidence clip.
- The unaltered authenticity of the original continuous recording segment stored in the primary video archive.

## 5. Security Boundaries & Network Trust Assumptions

### Identified Scope Items & Operational Controls
1. **`X-Forwarded-For` Header Trust:** The rate limiter reads client IPs from `X-Forwarded-For` when available. In production deployments, the backend API must be deployed behind a trusted reverse proxy (e.g., Nginx, Cloudflare) configured to strip/overwrite untrusted incoming `X-Forwarded-For` headers from public clients.
2. **DNS-Rebinding / TOCTOU Time-Window:** The SSRF proxy validator (`validate_proxy_url`) resolves hostnames during initial URL validation. To completely eliminate Time-of-Check to Time-of-Use (TOCTOU) DNS rebinding risks, production outbound proxies should use socket-level IP binding via a dedicated HTTP proxy daemon (e.g. Squid / Envoy).
